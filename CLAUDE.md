# Правила проекта

Файл для агентов и для тех, кто впервые правит этот код. Здесь только то,
что неочевидно из самого кода и что легко сломать по незнанию.

Обзор проекта — [README.md](README.md). Модель данных с обоснованиями —
[docs/data-model.md](docs/data-model.md). Известные грабли окружения —
[docs/dev-notes.md](docs/dev-notes.md).

## Команды

```bash
docker compose up               # всё окружение: БД, Redis, почта, приложение, воркер
npm test                        # юнит-тесты домена + тесты БД (нужен Postgres)
npm run test:e2e                # Playwright, нужно поднятое приложение
npm run lint && npm run typecheck
npm run db:migration -- <имя> <файл-в-prisma/sql>
DISABLE_NOTIFICATIONS=true npm run db:seed   # ВНИМАНИЕ: очищает базу
```

Перед коммитом должны проходить `lint`, `typecheck`, `test` и `build`.

## Границы слоёв

```
lib/domain    чистая логика, без базы и без new Date() внутри
lib/services  сценарии: транзакции, Prisma, побочные эффекты
app           транспорт: валидация → вызов сервиса → отрисовка
```

Правила, которые нельзя нарушать:

- **В `lib/domain` не импортируется `prisma`.** Всё, что влияет на результат,
  приходит аргументами — включая текущее время. Это не догма: именно поэтому
  переход на летнее время проверяется тестом без базы.
- **Бизнес-логика не живёт в `app/`.** Серверное действие валидирует вход
  через zod, вызывает сервис и превращает доменную ошибку в сообщение.
- **Модули с `import "server-only"` не импортируются в клиентские компоненты.**
  Если из такого модуля нужна константа или чистая функция — вынесите её
  в `lib/domain`, а не убирайте пометку. Один раз это уже поймало утечку
  Prisma в браузерный бандл.

## Что нельзя делать

**Не менять статус записи напрямую через Prisma.** Только через
`transitionAppointment`: там живут списание абонемента, создание платежа,
счётчик неявок и снятие напоминания. Прямой `update` создаст запись
в состоянии, из которого деньги не поступят.

**Не добавлять поле `remaining` в абонемент.** Остаток считается по журналу
`SubscriptionUsage`. Счётчик рассинхронизируется при первой же отмене
или ретрае задачи.

**Не считать выручку по `Appointment.priceMinorSnapshot`.** Только по журналу
`Payment`. Абонемент оплачен один раз, визитов по нему несколько.

**Не полагаться на проверку занятости в коде.** `isSlotAvailable` нужна
для внятного сообщения пользователю; гарантию даёт `EXCLUDE`-констрейнт.
Ловите `isSlotConflict(error)` и показывайте «слот только что заняли».

**Не редактировать применённые миграции.** Новое ограничение — новый файл
в `prisma/sql/` и новая миграция через `npm run db:migration`.

**Не запускать `prisma migrate reset` и `db:seed` не подумав.** Оба очищают
базу. На проде разрешён только `prisma migrate deploy`.

**Не добавлять том Docker на `/app/.next`.** Выглядит логично, но на macOS
оставляет каталог-точку монтирования, который потом не удаляется и утягивает
доступ ко всей папке проекта. Проверено дорогой ценой.

## Как добавить типовые вещи

**Услугу, абонемент, мастера** — это данные, а не код. Через интерфейс
или сид.

**Новое ограничение БД:**
1. Дописать SQL в `prisma/sql/NNNN_<имя>.sql`.
2. `npm run db:migration -- <имя> NNNN_<имя>`.
3. Добавить ожидаемое определение в `tests/db/constraints.structure.spec.ts`
   и поведенческий тест в `constraints.behavior.spec.ts`.

Шаг 3 обязателен: без него ограничение можно молча сломать при следующей
правке схемы.

**Новый тип уведомления:**
1. Значение в `NotificationType` (schema.prisma) + миграция.
2. Ветка в `notification_subject_valid` — субъект зависит от типа.
3. Обработка в `worker/index.ts`.

**Новую страницу администратора:** каталог в `app/(admin)/`, доступ
проверять не нужно — это делает `app/(admin)/layout.tsx`. Для клиентских
данных используйте `getCurrentClient()`, а не `clientId` из параметров.

## Стиль

- Комментарии объясняют **почему**, а не что. «Блокировка строки абонемента»
  бесполезно; «без неё два параллельных бронирования спишут последний сеанс
  дважды» — полезно.
- Комментарии и сообщения интерфейса на русском, идентификаторы на английском.
- Деньги — целые копейки, `Int`. Никаких `price / 100` в коде: есть
  `lib/domain/money.ts`.
- Время в базе и в коде — UTC. Локальное время существует только в паре
  с таймзоной салона, всё преобразование в `lib/domain/time.ts`.
- Ошибки, адресованные пользователю, — `DomainError` с текстом на русском.
  Всё остальное логируется и превращается в «попробуйте ещё раз».

## Тесты

- Чистая логика — `tests/domain`, без базы.
- Ограничения и конкурентность — `tests/db`, против настоящего Postgres.
  Здесь используется голый `pg`, а не Prisma: нужны точные SQLSTATE,
  а Prisma сводит нарушения CHECK к неструктурированной ошибке.
- Критический путь — `e2e`, включая чтение письма из Mailpit.

Тест, который проверяет только наличие имени ограничения, бесполезен:
подмена поля внутри определения его не уронит. Сравнивайте определение.
